# Supply Chain Verification

This repo uses the official SLSA GitHub Generator for release artifacts produced by the `SLSA Provenance` workflow:

- The release workflow checks shell syntax before packaging.
- Tags matching `v*` build a release tarball from the exact Git commit.
- Release artifacts include `SHA256SUMS`.
- `slsa-framework/slsa-github-generator` generates signed SLSA Build L3 provenance for the release tarball.

The badge means release artifacts have SLSA Build L3 provenance generated by the official reusable workflow. It is not a dynamic certification badge or repo-wide conformance claim; the proof is the generated `.intoto.jsonl` provenance that users verify.

For the SLSA model and levels, see [slsa.dev](https://slsa.dev/).

## Release Artifacts

For tag `vX.Y.Z`, the release workflow publishes:

```text
route10-vpn-client-vX.Y.Z.tar.gz
SHA256SUMS
*.intoto.jsonl
```

## Signing A Release

Every release archive is signed with a key that never exists in this repository
or in CI. This is what stops a compromised repository from shipping code to the
routers: the repository can produce a new archive, a matching `SHA256SUMS` and
fresh provenance, but it cannot produce a valid signature.

The signing key lives offline (`.release-keys/` is gitignored):

```bash
openssl ecparam -name prime256v1 -genkey -noout -out .release-keys/release-signing-key.pem
openssl ec -in .release-keys/release-signing-key.pem -pubout
```

The printed public key goes into `VPN_UPDATE_PUBKEY` in `project.conf`, which
is committed and is the only half that belongs on a router. It has to live
there rather than in `conf/`: `conf/` is not tracked, so a key placed there
would never reach a release tarball and a fresh install could never verify an
update.

Per release, once the release workflow has published the archive:

```bash
./scripts/sign-release-asset.sh vX.Y.Z
```

That downloads the *published* asset (a local rebuild can differ in bytes),
checks it against `SHA256SUMS`, signs it, uploads the `.sig`, then re-downloads
the signature and verifies it with the same vendored check the routers run.
Re-running is the fix after the workflow re-uploads the archive.

To sign a local file without touching a release, use `sign-release.sh`:

```bash
./scripts/sign-release.sh dist/route10-vpn-client-vX.Y.Z.tar.gz
# -> dist/route10-vpn-client-vX.Y.Z.tar.gz.sig
```

The check itself is vendored from `route10-update-verifier` into
`lib/vendor/route10-signature.sh`; refresh it with that repo's
`scripts/sync-verifier.sh`, and CI rejects a hand-edited copy by digest.

Upload the `.sig` next to the archive. `scripts/updater.sh` downloads it,
verifies it with `openssl dgst -sha256 -verify` against `VPN_UPDATE_PUBKEY`, and
refuses the update when the signature is missing or does not match. That check
cannot be disabled.

Because `project.conf` is preserved across updates, a bad release cannot
replace the public key that validates it, so key rotation requires an explicit
out-of-band edit of `VPN_UPDATE_PUBKEY` on the device.

Releases published before the key existed carry no `.sig` and are refused, so
`updater.sh force` cannot be used to reinstall an older unsigned tag.

### Installing the key on an existing device

A device installed before v1.2.0 has no `VPN_UPDATE_PUBKEY`. `project.conf` is
preserved across updates and the key is never taken from a release, so such a
device installs v1.2.0 and then refuses every later update until the key is
added by hand. This is the one trust decision that cannot be delegated to a
download.

On the device, back up the file and append the block from this repository's
`project.conf` (LF line endings, quotes included):

```bash
cd /cfg/vpn-custom
cp -a project.conf project.conf.bak.$(date +%Y%m%d)

VPN_UPDATE_PUBKEY='-----BEGIN PUBLIC KEY-----
… the three lines from project.conf …
-----END PUBLIC KEY-----'
```

Then confirm it parses and matches the expected fingerprint:

```bash
sh -c '. ./project.conf; printf "%s\n" "$VPN_UPDATE_PUBKEY"' > /tmp/pub.pem
openssl pkey -pubin -in /tmp/pub.pem -outform DER -out /tmp/pub.der
openssl dgst -sha256 /tmp/pub.der
# 3543a2ef92610536bd8aba32a0774bc4a11ff46111f63d81d72d1a1c0cccf80b
```

`updater.sh status` reports whether the key is present and parses, alongside the
installed version and whether a cron entry actually runs the updater. CI fails
when `project.conf` in this repository loses the key, because a release can
never repair that on a device.

## Verify A Release

Two checks answer different questions, and you want both before running an
archive on a router:

- **Provenance** answers "did this archive come from this repository?"
- **Signature** answers "did a human with the offline key approve it?"

Provenance alone is not enough: a compromised repository can produce a fresh
archive with valid provenance. Only the signature stops that, because the key
is not in the repository or in CI.

### 1. Check the signature

Get the trusted public key from a device you already trust (or a checkout you
already trust), **not** from the archive you are checking — verifying an archive
against a key packed inside it proves nothing.

```bash
ssh root@<router> "sed -n -e \"s/^VPN_UPDATE_PUBKEY='//\" -e \"s/'\$//\" \
  -e '/-----BEGIN PUBLIC KEY-----/,/-----END PUBLIC KEY-----/p' \
  /cfg/vpn-custom/project.conf" > release-pubkey.pem
```

Confirm it is the key you expect before trusting any result:

```bash
openssl pkey -pubin -in release-pubkey.pem -outform DER -out release-pubkey.der
openssl dgst -sha256 release-pubkey.der
```

The digest must be:

```text
3543a2ef92610536bd8aba32a0774bc4a11ff46111f63d81d72d1a1c0cccf80b
```

If it differs, stop. Either the key was rotated out of band (`VPN_UPDATE_PUBKEY`
is preserved across updates, so rotation is always a deliberate manual edit) or
you have the wrong key.

Then download the release and verify the archive:

```bash
gh release download vX.Y.Z --repo unflawed-code/route10-vpn-client
sha256sum -c SHA256SUMS
openssl dgst -sha256 -verify release-pubkey.pem \
  -signature route10-vpn-client-vX.Y.Z.tar.gz.sig \
  route10-vpn-client-vX.Y.Z.tar.gz
# Verified OK
```

`SHA256SUMS` alone only proves the download was not corrupted — an attacker who
replaces the archive can replace `SHA256SUMS` too. The `.sig` is the part they
cannot forge.

Releases published before the signing key existed carry no `.sig`, and both the
routers and this manual check will refuse them.

### 2. Check the provenance

Install the GitHub CLI and `slsa-verifier`, then:

```bash
slsa-verifier verify-artifact route10-vpn-client-vX.Y.Z.tar.gz \
  --provenance-path *.intoto.jsonl \
  --source-uri github.com/unflawed-code/route10-vpn-client \
  --source-tag vX.Y.Z
```

The verifier should confirm that the artifact was produced by `github.com/unflawed-code/route10-vpn-client` from the expected tag.
