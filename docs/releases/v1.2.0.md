# v1.2.0

This release makes the self-updater refuse anything it cannot verify, and fixes
two routing defects.

## Updates are now signature-verified

The updater checks every archive against three things before applying it:

1. the SHA-256 checksum in `SHA256SUMS`;
2. the SLSA Build L3 provenance for this exact tag;
3. a detached `.sig` made with the release key.

The signing key never exists in this repository or in CI, so a compromised
repository — or a compromised workflow token — can publish a new archive and
matching checksums, but cannot produce a signature the routers accept. The
public half is pinned in `project.conf`, which survives updates, so a bad
release cannot replace the key that validates it.

Verification fails closed: a missing, malformed or mismatched `.sig` refuses the
update. There is no flag to skip it.

Devices running v1.1.0 are unaffected — that updater has no signature check —
but the first update to v1.2.0 must be applied by hand, since v1.1.0 trusts
whatever it downloads. After v1.2.0 every update is verified.

## Fixed

- **IPv6 leak on IPv4-only tunnels with host targets.** The IPv4-only block
  chain was flushed on every `ifup`/`fw-reload`, and only subnet targets were
  re-added, so a tunnel configured with host targets leaked IPv6 after any
  firewall reload. Host targets are now scoped by client MAC, resolved from the
  neighbour table and falling back to the DHCP lease table.
- **Hotplug scripts failed under dash.** The generated routing, split-tunnel and
  DHCP hotplug scripts locked with file descriptors 200-202, which BusyBox ash
  accepts but dash does not, so they exited at `exec 201>` on Debian-family
  `sh`. The locks now use single-digit descriptors and work in both.

## Updating to this release

v1.1.0 does not check signatures, so moving to v1.2.0 is the one update that
has to be applied by hand — this is the only time you verify an archive
yourself before it reaches a router. Afterwards the device checks every update
on its own and refuses anything unsigned.

Commands and the expected key fingerprint are in
[SUPPLY_CHAIN.md](https://github.com/unflawed-code/route10-vpn-client/blob/main/SUPPLY_CHAIN.md).
